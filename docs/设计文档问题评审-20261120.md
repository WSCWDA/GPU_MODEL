## 1. 结论摘要（先看这 7 条）

1. **最严重的问题不是某一章写错，而是"冻结—扩展"没有配套机制。** 第 1 章冻结 `Result` 11 值、19 个配置键、包类型表；后续章为了表达"FIFO 满""栈溢出""寄存器溢出"，直接引入 `Busy`/`OutOfStack`/`RegisterOverflow`/`InvalidIr`，而每章回归项又要求 "A1~A(n-1) 全绿"。**旧 DoD 与新契约必然互斥**，且文档没有定义"DoD 修订"这一动作（§4.1 详述）。
2. **MMIO 存在三套互斥地址表**：第 2 章（E 阶段最小环）、第 10 章（CP）、第 32 章（多队列"单活动窗口 + FW 重编程"）。三处对 `0x04`、`0x08`、`0x10`、`0x30` 的用途完全不同，而 `D10.1` 明确要求"第 2/10 章偏移表与代码逐项一致"——这条 DoD 目前不可能通过（§4.2）。
3. **ADR-047 的"37 管硬件通路 / 38~42 管驱动"只写在章首引言，没有落到任务。** 第 37 章 `T37.2/T37.6/T37.7/T37.10/T37.11/T37.12/T37.13` 与第 39/40/41 章的任务和 DoD 几乎逐条重复（8 对 DoD 内容相同）。同一能力被签约两次、实现两次、验收两次（§4.7）。
4. **第 19 章把"两后端逐字节一致"定为唯一判据，等于把第 20 章永久锁死。** 两个**独立实现**的指令选择 + 寄存器分配要产出逐字节相同的 blob，除非第二个后端复刻第一个后端的全部决策——那样"独立对照"的意义就消失了（§4.8）。
5. **第 31 章的并行策略实际是"带票号的串行"。** `ticket = fetch_add(nextTicket)` → 自旋到 `servingTicket == ticket` → 执行完 `servingTicket++`，每个 CU 同时只有 1 个 wave 在执行。于是 `maxWavesPerCu=16` 无意义，S11 的"并行一致性/竞争暴露"目标落空（§4.9）。
6. **第 36 章的 watchdog 在同步执行模型下不会触发。** watchdog 靠"每 tick 喂狗"，而单线程同步 `Execute()` 在死循环着色器内部不会返回、tick 无法推进。`D36.4`（死循环触发复位）缺一个指令预算/迭代计数机制（§4.10）。
7. **第 35 章的负荷与"单任务 ≤2 人日"规则结构性不符。** 22 个任务里包含"全 E/S 场景迁到 HLI"（1 个任务）+ 3 套完整 UMD（Vulkan / D3D12 / GL），每一项都是周级工作量（§4.11）。

## 3. P0 专项详述

### P0-01　`Result` 枚举：冻结 11 值 vs 全项目 4 处新增

**证据**

- 第 1 章 §3.2：`Result` 取值固定为 `Ok / InvalidArgument / NotSupported / NotMapped / NotResident / InvalidPacket / InvalidIsa / OutOfMemory / DeviceLost / ResetRequired / Internal`（11 个）；`D1.1` 断言"`Result` 恰 11 个取值无重复"。
- 第 10 章 §3.2 / `D10.10`：FIFO 满 → `Push` 返回 **`Busy`**。
- 第 13 章 §3.2、第 23 章 `D23.5`：同样返回 **`Busy`**。
- 第 15 章 §4.1 / `D15.5`：栈深超限 → **`OutOfStack`**。
- 第 18 章 §3.1：`Result result; // Ok / RegisterOverflow / OutOfMemory / InvalidIr`。
- 第 36 章 `D36.1`：判据文字为"**`Result` 枚举扩展冻结**"。

**为什么是 P0**

1. `Result` 是所有跨层接口的返回类型（第 1 章明确"所有跨层接口返回 `Result`，禁止异常跨层传播"）。新增值不是"加一个名字"，而是改动全项目最大公约数的契约。
2. 若新增：`D1.1`（恰 11 值）立刻失败；而第 2 章起的每章回归项都写 "A1~A(n-1) 全绿"，于是**第 10 章一旦落地 `Busy`，A1 就红**。
3. 若不新增：`D10.10`、`D15.5`、`D18.11`、`D23.5` 无法实现，四章验收不可能通过。

**建议（二选一，必须显式裁决）**

- **方案 A（推荐，语义更干净）**：`Result` 增加 4 值（`Busy`、`OutOfStack`、`RegisterOverflow`、`InvalidIr`），同步：① 第 1 章 §3.2 与 `D1.1` 改为"15 值"；② 第 1 章 §10 允许"契约变更"流程从"新建 ADR"改为"ADR + 修订前序 DoD 并留档"；③ 全项目搜索 `Result` 断言脚本改为"值集合快照比对"，而不是"恰 11 个"。
- **方案 B（不改 `Result`）**：`Busy` 用 `Ok` + 显式 `bool` 出参；`OutOfStack`/`RegisterOverflow`/`InvalidIr` 归入已有的 `InvalidIsa`/`OutOfMemory`，并在错误记录 `ErrorRecord` 里加 `detail` 字段区分。代价是语义模糊度上升。

> 无论选哪个，**第 36 章 `D36.1` 的"Result 枚举扩展冻结"这句话必须删掉**——它字面上否认了第 1 章的冻结，是当前最容易被误读的一处。

第 32 章又给出第三种模型：**"MMIO `0x00~0x0F` 只保留一个活动 ring 窗口，ring 描述表（base/size/head/tail）放 GPU 内存，FW 切换队列时重编程窗口"**。这与第 2/10 章"每队列一组 `RING_BASE/SIZE/HEAD/TAIL` 寄存器"在结构上互斥。

**为什么是 P0**

- `D10.1` 明确要求"**第 2/10 章偏移表与代码逐项一致（脚本比对）**"——按现在的表，脚本一定会报 5 处不一致：`0x04`、`0x08`、`0x10`、`0x30`，以及 `0x03` vs `0x01` 的 head 语义。
- `D3.6` 要求 `RT_SIZE(0x30)=0x0100_0100`；而 `D10.x` 会往同一地址写 `DEV_RING_ID`。**两个 L1 阻断判据会互相破坏对方的状态**，不是"文档不一致"，是"测试互相打脸"。
- ch6 的 `0x80~0xDF` 会被 ch10 的"非法偏移"判据拒绝，`D6.2` 与 `D10.3` 不能同时为真。

**建议**：第 10 章升格为 MMIO 唯一权威表（它已经自称"`../design/command-mmio.md` §4，本章落地"），并做三件事：
1. 把 `RT_SIZE` 从 `0x30` 迁到 `0xE0`（仍留 256 dword 内），`DEV_RING_ID` 保留 `0x30`；
2. 显式登记 `0x80~0xDF` 为"PSO 暂存区（ch6 所有），第 20~26 章只增不改"；
3. 第 2 章改为"第 10 章的子集视图"，`D2.2` 的断言范围缩到"本章已登记偏移"，不再声明 `0x40~0xFF` 全部 `NotSupported`（见 P1-04）；
4. 第 32 章的"单活动窗口 + 内存 ring 表"要么降级为二期（capability），要么明确"E/A 阶段用直连寄存器，E 阶段结束后切换"——不能与 2/10 章同时作为一期实现。

### P0-03　"A1~A(n-1) 全绿"与"契约可扩展"互斥

**证据**：几乎每章的回归项都写 "A1~A(n-1) 全绿"，但同时：

- `D2.2`：`0x40~0xFF` 保留段读写应返回 `NotSupported`。而 ch3 用 `0x40~0x4F`（stateId 表）、ch6 用 `0x80~0xDF`、ch10 用 `0xF0`、ch20/33/34 用 stateId。
- `D5.1`：`opcode` 表与 §3.2 逐项一致（20 条）。ch15 加控制流 `0x30~0x3F`、ch30 加原子 `0x40~0x4F`、ch28 加 `0x60~0x6F` 后，第 5 章的表必然不再是权威。
- `D6.2`：`0x80..0xDF` 回读与 `SHADER_PSO` 载荷逐一相等。ch20 用管线对象替代 PSO 包（`T20.15`）后，该断言失去输入来源。

**为什么是 P0**：这不是某一章写错，而是**治理机制缺口**。文档只定义了"契约变更走 ADR + 回归"，没有定义"**前序章的 DoD 如何随契约变更修订**"。结果是：任何合法的能力扩展，都会让"历史全绿"变成永久红灯。项目越往后推进，红灯越多，最终只能靠"不跑老用例"来维持门禁——门禁形同废止。

**建议（机制层，优先级最高）**

1. 在 `roadmap.md` §7.4 增加**DoD 修订条款**：后续章可修订前序章的判据，但必须 ① 有 ADR；② 在 `roadmap.md` 登记"`D-nn` 由 `D-mm` 取代"；③ CI 里旧判据标记 `SUPERSEDED` 并指向新判据，而不是删除。
2. 把"断言范围"从"全局常量"改为"**本章已登记集合**"：`D2.2` 改成"本章 §3.3 表内偏移"，`D5.1` 改成"本章子集内的作操码"，`D6.2` 改成"本次 `SHADER_PSO` 实际写入字段"。
3. 增加**契约快照 CI**：`Result` 值集合、MMIO 偏移表、`PKT_TYPE/SubOp` 注册表、`stateId 0~31` 映射表、S 场景子 case 表——五张表每次提交做快照 diff，变更必须附带 ADR 号。

### P0-04　`BARRIER(0x0E)`：一个包号，四种载荷

| 章 | 载荷 | 语义 |
|---|---|---|
| 20 §3.4 | `{srcStageMask, dstStageMask, accessMask}` | 资源状态转换（触发 ch12 flush/invalidate） |
| 30 §3.3 | `{memOrder, scope}` | 组内/设备内存序与作用域 |
| 32 §3.3 | `{srcStageMask, dstStageMask, accessMask, acquire/release}` | 队列所有权转移 |
| 41 §3.2 | `{scope ∈ {Workgroup,Device}, access ∈ {READ,WRITE,RW}}` | 计算侧作用域收口 |

**为什么是 P0**：`count` 与 `packet-specific` 字段只有一份。四种载荷的字段数、位宽、语义都不同，解析器无法同时识别；CP 只能按"第一个 4 字节"猜语义。且第 1 章已把 `0x0E` 登记为"落地章 32"，实际却是 20/30/32/41 四章都在写它——**登记表与实现面不符**。

**建议**：`0x0E` 统一为"**粗粒度、统一信封 + 子类型**"：
```cpp
struct BarrierPkt {
    u8  kind;        // 0=resource, 1=execution(组内/设备), 2=ownership(acquire/release)
    u8  scope;       // Workgroup / Device / QueueFamily
    u8  memOrder;    // Relaxed/Acquire/Release/AcqRel/SeqCst
    u8  accessMask;  // READ/WRITE/RW 位
    u32 srcStageMask, dstStageMask;
};
```
一次 ADR 统一四章，之后 `D20.10/D30.x/D32.x/D41.x` 全部重写为"同一信封的不同 `kind` 组合"。

### P0-05　`block` 上限：1024 允许 / 512 隐含 / 1024 拒绝

**证据**

- 第 39 章 §3.3：`block 各维 ≥1 且积 ≤1024`（**允许 1024**）。
- 第 39 章 §3.3 同段：`wavesPerGroup ≤ 16`（B-037）→ 1024 线程 = 32 wave，**必然超限**。
- 第 37 章 `D37.1`：`D13-a/b/c（block 1024 / LDS 128 KiB / grid 2^20+1）记录期 InvalidArgument`（**1024 必须拒绝**）。
- 第 41 章 `M-03`：`wavesPerGroup` 同 CU 整体驻留 → 1024 线程组根本无法驻留。

**为什么是 P0**

1. 同一章内两句话互相否定（`≤1024 允许` 与 `≤16 wave ⇒ ≤512`）。
2. 第 37 章与第 39 章是**同一契约的两个副本**，一个说拒绝、一个说允许；stage3 的 A39/A37 会得出相反结论。
3. 数值 1024 的来源不明：`bit-budget.md` 的 B-036~B-041 只登记了 LDS 64 KiB、wave 16、grid 2^20、FIFO 8、描述符 64K、参数 4 KiB，**没有"最大 block 1024"这一条**。

**建议**：定一条并登记 B 号：
- 若以 B-037 为准：`maxThreadsPerGroup = 16 × 32 = 512`，`D37.1` 的"D13-a block 1024"改成 `block 512+1` 或直接 `block (32,32,1)`；
- 若产品上要允许 1024：必须同时把 `maxWavesPerCu` 提到 32，并重算 LDS/VGPR/SGPR 容量与 30 章 barrier 可达性证明。两者不能都"看起来成立"。

### P0-06　`DISPATCH_INDIRECT` 参数布局：12 B vs 28 B

- 第 33 章 §3.2：`dispatchIndirectArgs { u32 gridX, gridY, gridZ; }`（3 dword）。
- 第 41 章 §3.3：`DispatchArgsIndirect{grid[3], block[3], reserved0=0}`（7 dword，16 B 对齐）。

**影响**：`D33.4`/`D37.11`/`D41.5` 都要求"与直接 dispatch 逐值等价"。若按 12 B 读，`block` 从哪来？若按 28 B 读，ch33 的 CP 会越读 16 B，可能踩到相邻数据并被 `NotMapped` 中止。这不是"版本差异"，是同一 SubOp 的两种载荷。

**建议**：定 28 B（含 `block` 才能"与直接等价"），ch33 的 `D33.4` 改为"读 28 B 后与直接 dispatch 等价"，并在 `bit-budget` 登记 `SubOp 0x0010` 的载荷长度；或者二选一：一期只支持 grid（block 随包），二期再扩——但必须写进 capability 表，且 `D41.5` 不能要求 `block` 间接化。

### P0-08　第 19 章"两后端逐字节一致"：不可达的判据

**证据**

- 第 19 章章首：`"两后端逐字节一致"是本单元的唯一判据`；`19 未过不进入第 20 章`。
- §3.2 说明：`blob_LLVM` 由**独立于第 18 章的发射实现**产生，**不调用手写后端 emit**（Q-50）。
- `D19.2`：全 S3 着色器，`blob_A` 与 `blob_LLVM` 逐字节一致。

**为什么不可达**

1. 逐字节一致意味着：指令选择、立即数展开（MAD → MUL+ADD 的取舍）、块序、寄存器分配（线性扫描的溢出决策）、栈帧布局、NOP/对齐填充，**全部决策必须相同**。
2. 而"独立实现"要求第二个发射器**不能调用**第一个的实现。它只能靠"读同一份 IR + 同一份规则表"来复现；一旦规则表相同，它就不是独立对照，而是同一算法的第二份拷贝——此时"一致"只证明了"两份拷贝写得一样"，不证明"语义正确"。
3. 只要 LLVM 侧走真实的寄存器分配/调度（这是引入 LLVM 的意义），输出必然与手写线性扫描不同。**要么放弃独立，要么放弃逐字节。**

**影响**：第 20 章永久无法开工（roadmap 规定 19 未过不进 20），整个 C 阶段被单点阻塞。这是全项目最大的进度风险。

**建议**（把判据换成"可判定且有意义"的三层）：

| 层 | 判据 | 说明 |
|---|---|---|
| L1 | **规范化指令序列等价**：两边 blob 经同一反汇编器 → 去掉 NOP/对齐/寄存器名重命名 → 逐 opcode+操作数结构比对 | 允许寄存器号不同，不允许指令语义不同 |
| L2 | **语义等价**：同一输入在解释器 + LLVM JIT 下输出逐值一致（整数零容差、fp ≤1 ULP） | 这是真正想验证的东西 |
| L3 | **编码一致性**：随机抽 20% 函数，两边对同一 `(opcode, operands)` 调 `encode()` 得同字节 | 只验证编码器，不验证分配器 |

把 `D19.2` 改为 L1+L2 组合，`D19.9` 的"A19 全绿"才可能通过。

### P0-09　第 31 章并行策略：ticket 锁把 CU 内执行串行化

**证据（§4.2）**

```
波生成 → ticket = fetch_add(nextTicket) → 自旋等待 servingTicket == ticket
→ 领取并执行；完成后 servingTicket++
```

**推理**

1. 只有 `servingTicket == ticket` 的波能执行，且**执行完才 `servingTicket++`** → 任一时刻每 CU 只有 1 个 wave 在跑。
2. 于是 `maxWavesPerCu = 16`（B-037）永远达不到；occupancy 账本（§4.3）退化为"恒为 1"。
3. 第 30 章的组内 barrier（"组内全部 wave 到达才放行"）在串行执行下变成"每个 wave 依次到达、计数先到 1 再累加"——**跨 wave barrier 永远不会真正"同时等待"**，其正确性证明（M-03 组整体驻留防死锁）失去测试意义。
4. `execution-parallel.md` 对策略 B 的目标是"硬件对齐并行、暴露竞争 bug"。串行执行下**没有竞争可暴露**：线程本地 TLB + 全局失效（`D31.16`）也不会真正触发脏读。
5. 更隐蔽的一点：`fetch_add` 的**顺序取决于线程调度**，所以"哪个 wave 拿到 ticket 0"不确定；`D31.12` 要求"ticket 波领取序逐项一致"（serial 与 parallel 之间），这只有在"每 SE 单 worker"时才成立。`se_count=1, worker_threads=4` 时必然不稳定。

**建议**

- 把 ticket 从"执行许可"降为"**确定性编号**"：`ticket = 由 (seId, waveIndexInQueue) 静态计算`，不再 `fetch_add`；执行仍由 CU 的 slot 池并发调度（`resident ≤ maxWavesPerCu`）。
- 若确实要 ticket 保序，则必须承认"策略 B ≈ 多线程搬运 + CU 内串行"，并从目标里删掉"暴露竞争"，同时把 `maxWavesPerCu` 改成 1（否则是自欺）。
- 无论哪种，`D31.12` 的"领取序逐项一致"要改成"**执行完成序按静态编号可复现**"，并给出证明方式（例如每波带 `(seId, waveIdx)` 记录）。

### P0-10　第 36 章 watchdog：同步模型下没有 tick 源

**证据**

- §4.2：`每 tick：各引擎 OnEngineProgress（若有包在处理）`；`active[engineId]` 超限触发复位。
- `D36.4`：死循环着色器触发 watchdog，只复位该引擎。
- 而全项目执行模型是同步的：第 2 章 `Submit` 注释"同步执行完命令"；第 15/25 章的 shader 执行在 `Execute()` 内完成；`execution-parallel.md` 规定不依赖墙钟。

**为什么不可能**

死循环着色器在 `IShaderArray::Execute()` 的 `while` 里永不返回 → 调用栈不回到 CP → **没有任何地方能推进 `tick`** → watchdog 永远等不到"超限"。要么整个进程挂死（这与 `D36.4` 的"只复位该引擎"矛盾），要么需要"指令预算"在 ISA 执行器内部计时。

**建议**

1. 在第 15 章（控制流）增加**每波指令预算**：`kMaxInstructionsPerWave`（例如 `2^24`），超预算 → `InvalidIsa` + `ErrorRecord{code=Internal, detail=Budget}`；
2. watchdog 判据改为"**预算耗尽 + 无进展计数**"，tick 由"每执行 N 条指令"推进，而不是外部定时器；
3. `D36.4` 改为"死循环在预算耗尽后被确定性中止并复位该引擎"，可机器判定；同时补一个"预算不误伤合法长 kernel"的反例（S19 大 grid 回归）。

### P0-11　第 35 章：22 任务 / 3 套 UMD / 4 次大爆炸

**证据**

- `T35.04`：`场景直连 HLI 全 E/S 跑通`（一个任务 = 全项目场景迁移）。
- `T35.05`：`A35.1 全绿后才 35.2`；`T35.10/T35.15/T35.20` 分别要求 Vulkan/D3D12/GL 在"**全部 E/S**"上与 `hli` 逐字节一致。
- 全章 22 个任务（本批文档中最多）；`roadmap.md` 规定单任务 ≤2 人日。

**为什么不可执行**

1. "全 E/S 迁移到 HLI"不可能 ≤2 人日：它要改 20+ 场景的入口、资源创建、状态绑定、同步路径。
2. 3 套 UMD（Vulkan 资源/视图/管线/命令表、D3D12 资源/视图/PSO/列表、GL 状态机）是三个独立的适配层，每套都是"多月"量级；文档用 3 个任务（T35.07~T35.09 等）表达，粒度失真 10 倍以上。
3. 四次串行门禁（35.1→35.2→35.3→35.4），任何一次卡住，后续全停；而 35 章处于 E 阶段末尾，是 38~42 的前置——**它一卡，stage3 全卡**。

**建议**

1. 把 `M35.2/M35.3/M35.4` 各升格为独立章（或独立 stage），每套 UMD 单独 A 验收、单独回退；
2. 明确 **D3D12/GL 的能力档**：若人力不足，允许降为 `capability=false`（`NotSupported`）并在 roadmap 标注"二期"，不要与 Vulkan 同期硬扛；
3. `T35.04` 拆成"E 场景 → HLI"与"S 场景 → HLI"两个任务，并允许"场景双入口并存期"（旧直连 + 新 HLI 同时跑，逐场景切换），避免一次性大爆炸；
4. 在 roadmap 增加**容量测算**：以 35 章为锚，反推 3 套 UMD 的人月，再校验总计划是否成立。

## 4. 其余 P0 相关专题（与上面 11 项交织，单独说明影响面）

### 4.1 "冻结—扩展"机制缺口（P0-01/P0-03 的共同根因）

现有流程是"**新建 ADR → 更新契约文档 → 更新 DoD/判据 → 回归**"。缺的是两件事：

1. **旧 DoD 的退役**：没有 `SUPERSEDED` 状态，旧判据要么删（丢证据），要么留（永久红灯）。
2. **判据的"作用域"**：所有 DoD 都写成全局断言（"0x40~0xFF 全部 NotSupported"、"恰 11 个 Result"），而不是"本章登记集合内"。

建议把 `roadmap.md` §7.4 扩成三步：`ADR → 契约文档 → 判据作用域收敛 + 旧判据 SUPERSEDED 登记`。这是本次评审中**唯一一条"改一处、收益覆盖全项目"的修订**。

### 4.2 MMIO 冲突的连带影响

除 P0-02 外，它还导致：

- `D3.6`（RT_SIZE 读回）、`D6.2`（PSO 暂存区回读）、`D10.1`（两章一致）、`D10.3`（非法偏移拒绝）四个 L1 判据互相破坏；
- 第 32 章的多队列模型无法落地（要么改 2/10 章，要么 32 章方案作废）；
- `boot-reset.md` 的 `RESET_CTRL(0xF0)` 与第 2 章的"保留段"冲突（同 P1-04）。

### 4.3 分阶段门禁与"前向依赖"

按文档，"A<x> 全绿才能开下一章"，但至少 8 处 DoD 依赖后面的章：

| 章 | 依赖 | 依赖内容 |
|---|---|---|
| 11 `D11.9` | 12 | `CacheSubsystem` 的 flush/invalidate |
| 17 `A17`/`D17.14` | 18 | 端到端出图需要后端 |
| 22 `D22.8` | 28 | S6 场景 |
| 24 `D24.x` | 28 | S6 归属 |
| 27 `§10` | 31 | tile 缓冲与并发物化 |
| 28 `Q-59` | 30 | patch 缓冲与 LDS 合并 |
| 38 `D38.2` | 40 | stream 同步校验 |
| 37 `T37.6~T37.13` | 30/31/33/34 | 复述后者能力 |

其中 17→18 与 38→40 是**硬阻塞**（前者让 A17 永红，后者让 D38.2 无对象可测）；其余可以通过"空实现 + 语义仍成立"降级（文档已有此写法，但没有统一模板）。

建议：在 `roadmap.md` 增加"**依赖登记表**"，明确每个前向依赖是"硬依赖（不得开工）"还是"软依赖（可空实现，语义保持）"，并要求章首写明。现在这些依赖散落在各章 §10，没人能一眼看出关键路径。

### 4.4 任务粒度：文档里的"≤2 人日"是纸面规则

抽查结果（任务数 / 明显超 2 人日的任务）：

| 章 | 任务数 | 超粒度任务 |
|---|---|---|
| 35 | 22 | `T35.04` 全场景迁移；`T35.07~09` 整套 Vulkan UMD；`T35.12~14` 整套 D3D12；`T35.17~19` 整套 GL |
| 16 | 11 | `T16.3` 汇编器（tokenizer + 两遍 label + 类型推断）；`T16.7` 全 opcode 解码；`T16.8` 每 opcode 正反例 |
| 28 | 16 | HS/Tess/DS/GS 四条特性 + patch 缓冲 + 边界用例 |
| 31 | 16 | 并行底座（SE/CU/ticket/TLB/occupancy）整体 |
| 37 | 14 | 吸收 20 章打包 + 35.5 launch + 30/33/34 收口 |
| 20 | 16 | 描述符堆 + 根签名 + 管线 + 采样器 + 绑定替换 |

建议：凡是"一整套子系统"或"全场景迁移"的任务，必须拆到"接口/主体/接入/验收"四段各 ≤2 人日；否则 roadmap 的粒度规则只是装饰。
