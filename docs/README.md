# GPU_MODEL：CPU 模拟 GPU 教学项目

> 当前任务主干（2026-11-24）。项目以九个教学单元 U0–U8 组织，不再沿用旧版 42 章作为开发排期。本文决定学习目标、范围与最终成果；[教学任务路线图](roadmap.md)给出每个单元的任务与通过条件；[架构设计](architecture-design.md)规定需要共用的模块边界。

## 1. 项目要教会什么

学习者完成项目后，应能沿着一条实际运行的记录解释：

1. 图形 draw 如何形成命令，经提交、取命令、顶点处理、固定功能管线写入图像；
2. 计算 dispatch 如何把 kernel 分给 workgroup、wave 和 lane，并读写资源；
3. 图形与计算如何复用命令、内存、执行、同步以及 HLI/KMD/FW 底座；
4. CPU 线程如何承载模拟器任务，为什么宿主 CPU 的缓存行为和软件模拟的 GPU 缓存属于两个不同层面；
5. 一项结果从哪里来：输入、关键状态、同步点、参考结果与导出的图像或数据。

这是功能和原理教学模型。它不承诺周期精度、真实 GPU 性能、厂商指令集或完整图形/计算 API 兼容。教程可以采用便于观察的简化数据和算法，只需说明简化所代表的概念和适用范围。

## 2. 教学组织方法

每个单元围绕一个可回答的问题，完成一个最小可运行练习，再通过改变一个输入或开关观察行为。一个教学单元可以有多个小实验；不以接口字段数量、精确硬件常数或覆盖全部旧场景作为完成标准。

| 层次 | 要求 | 允许的简化 |
|---|---|---|
| 共享核心 | 图形与计算使用同一套命令提交、资源访问、执行调度入口、完成/可见性语义 | 具体包编码、容量、调度策略可随实现迭代 |
| 单元实验 | 输入、预期输出和关键观测点在本实验内自洽 | 可使用局部模拟器、替身对象、独立参考实现 |
| 综合演示 | 选定的一条图形路径和一条计算路径通过共享核心连通 | 不要求所有教学实验汇入同一个大型程序 |
| 扩展实验 | 用独立场景解释某个高级机制 | 不成为主路径、其他单元或最终演示的前置条件 |

**判断冲突的方法**：如果两个实验使用不同的纹理过滤近似、缓存容量、细分因子或指令编码，只在各自实验内说明即可。如果它们通过同一资源、命令或 fence 交换数据，就必须遵守共享边界对命令含义、资源读写、完成和可见性的约定。允许局部差异，不允许最终集成路径把未完成的写入当成已完成或把两套不兼容的资源地址混用。

### 2.1 从第一张图开始

U1 先用内置的属性传递顶点处理得到清屏和三角形图像。U2 再以小型 wave/ISA 执行器替换这个顶点处理入口，观察可编程部分改变了什么。U4 继续扩展纹理、深度和混合。Tessellation/GS 作为独立的几何扩展实验，不阻挡首帧和后续计算任务。

### 2.2 学习路径可以分支

完成 U0 后可先做 U3（内存与资源）；完成 U1 后，U2（着色执行）与 U4（图形扩展）可以按兴趣交错学习。U5 使用 U2/U3 的概念完成计算协作；U6 把已有命令和资源放进共用驱动底座；U7 分别接图形 UMD 与计算 UMD；U8 只集成选定的可运行路径。实际开工条件见路线图，不按旧章号线性推进。

## 3. 新任务划分

下表是**当前唯一的开发任务主线**。U 表示教学单元，单元内任务编号见 [roadmap.md](roadmap.md)。旧版 WP0–WP8、EDU-00–EDU-18、1–42 章不映射为一一对应的新任务。

| 单元 | 核心问题 | 最小可见成果 | 依赖 |
|---|---|---|---|
| U0 可运行与可观察 | 如何让一个模型实验可重复、可定位？ | 命令行场景、输入快照、分级日志和结果文件 | 无 |
| U1 命令与第一帧 | 一条 draw 怎样变成像素？ | 清屏、三角形、提交/CP/fence 记录、导出图像 | U0 |
| U2 可编程着色 | wave/lane 和指令怎样替换内置顶点处理？ | 同一三角形经小 ISA 执行，另有单 wave 计算练习 | U0、U1 |
| U3 内存与资源 | 地址、视图、缓存和可见性怎样影响读写？ | 映射/别名与 flush 实验，能指出数据存放位置 | U0；与 U2 可并行 |
| U4 图形管线扩展 | 固定功能、纹理和几何阶段怎样组合？ | 纹理、深度/混合图像；独立 Tess/GS 扩展图 | U1；部分练习使用 U2/U3 |
| U5 计算与协作 | wave/workgroup 怎样协作，CPU 怎样并行承载？ | vector_add、组内归约、串行/并行结果对照 | U2、U3 |
| U6 共用驱动底座 | HLI、KMD、FW 怎样把两类命令送到同一模型？ | 两类最小命令共用提交、资源和完成路径 | U1、U3；计算接入使用 U5 |
| U7 图形与计算 UMD | 两种用户态入口怎样使用同一底座？ | 图形 draw 和计算 launch 分别从 UMD 提交 | U5、U6 |
| U8 综合演示与教程 | 两条路径怎样交换数据并解释结果？ | 计算写资源、图形读取并导出一帧；端到端导览 | U4 的基础部分、U7 |

U4 的 Tess/GS、U2 的编译器前端、U3 的缓存替换策略、U6 的复杂故障恢复和 U7 的外部 API 适配器均有教学价值，但不阻断 U8。它们可以在对应单元的基础练习完成后独立扩展。

## 4. 共用内核与模块归属

目录采用 [architecture-design.md](architecture-design.md) 的驱动层次。早期练习可使用轻量替身，U6/U7 再接入真实分层。**共用的含义是共享最小行为与接口，不要求每个实验共用全部内部数据结构。**

| 模块 | 必须共用的行为 | 可以局部变化的内容 |
|---|---|---|
| common 与命令模型 | Draw、Dispatch、Copy、Signal/Wait 的含义及参数归属；可追踪提交标识 | 编码位宽、包布局、调试字段 |
| hw_sim/core 与提交 | 命令进入、消费、完成以及可观察的 fence 先后 | ring 容量、推进策略、局部状态机表示 |
| hw_sim/memory | 资源标识、地址边界、读写和显式可见性 | flat/paged、TLB、L1/L2 的教学实现 |
| hw_sim/shader | VS/CS 所需的调用与结果接口；lane 不越界写入 | 最小 ISA 指令集合、寄存器表示、优化方法 |
| firmware/KMD/HLI | 同一个提交与资源对象向图形、计算两入口提供服务 | 课堂实验所用替身、后续队列调度细节 |
| umd/graphics 与 umd/compute | 共享底座对象及完成语义 | 各自的 API 形状、对象包装和可选适配器 |

GPU 模型中的 L1/L2 是显式软件机制，可用命中、失效和 flush 记录解释数据流；宿主 CPU 的 L1/L2/L3 只影响模拟器速度。几何阶段的 patch/control-point 和 GS 输出可作为局部暂存实验，不能自动等同于通用 GPU cache。U5 的 CPU worker 应以 workgroup 或独立 tile 为任务粒度；barrier 是模拟器中的逻辑同步，不靠阻塞所有宿主线程实现。

## 5. 教学展示与通过条件

| 检查点 | 现场演示 | 能解释的原理 |
|---|---|---|
| C1 第一帧 | 从场景提交 clear/draw，导出三角形图 | 命令、顶点、裁剪/光栅、OM、fence |
| C2 可编程替换 | 内置顶点处理与 wave/ISA 路径产生预期图像 | 固定功能与可编程阶段的边界 |
| C3 资源流动 | 同一数据经历映射、视图、暂存/缓存和 flush | 地址翻译、复用、可见性与宿主缓存区别 |
| C4 计算协作 | vector_add 和跨 wave 归约在串行/并行执行 | grid/workgroup/wave、LDS、barrier、原子 |
| C5 双驱动入口 | 图形 UMD 与计算 UMD 各提交最小任务 | 两种入口如何共用 HLI/KMD/FW/CP |
| C6 综合帧 | 计算写缓冲，经同步后作为图形输入导出图像 | 队列依赖、资源所有权与端到端数据流 |

每个检查点只要求自身明确的输入、预期结果、错误行为和可读的运行记录。整数和像素等确定结果按该实验的参考值验证；浮点实验先声明容差和归约顺序。仅对已定义、无数据竞争的负载比较串行与并行结果。没有把“此前所有旧章的 A 门禁全绿”作为进入下一单元的条件。

## 6. 最终交付

- 可从干净检出构建的 CPU 软模型、headless 场景运行器、统一的基础命令/内存/执行/同步接口；
- C1–C6 的最小输入、图像或数据输出、参考结果和可阅读的关键步骤记录；
- 一份按 U0–U8 逐步学习的教程：先运行，观察关键状态，再修改一个参数，最后解释结果；
- 每个高级扩展实验单独标明适用范围和与共用核心的连接点；可选窗口仅用于展示，机器判据读取导出的数据。

日志按 Error/Warn/Info/Debug/Trace 分级，热点路径默认关闭细粒度输出；错误应给出模块、场景和相关命令/地址/执行位置。统计区分模拟 GPU 的模型事件与宿主 CPU 耗时，不能用模拟器的运行时间推断真实 GPU 性能。

## 7. 旧资料的使用方式

[旧版 42 章任务表](stage1/)以及 [stage2](stage2/)、[stage3](stage3/) 中的章节文档保留为算法、接口和测试向量资料，不再决定任务顺序或跨章节硬门禁。[场景规约](design/scene-specs.md)中的 E/S 场景可选作输入和参考；U0–U8 的检查点以本版路线图中的实际练习为准。旧版主干内容可在 [重组前提交](https://github.com/WSCWDA/GPU_MODEL/commit/0b36b1d6dcdc25e1bcc958c5be642653943d0c7c) 查看。

源码阅读建议按问题选取：图形 UMD/PAL 和资源路径参考 [Mesa](https://www.mesa3d.org/)；计算对象和使用方式参考 [MUSA 文档](https://developer.mthreads.com/musa)及公开的 [torch_musa](https://github.com/MooreThreads/torch_musa)；wave、内存和同步概念可交叉查阅 [AMD ROCm](https://rocm.docs.amd.com/) 与 [NVIDIA CUDA 文档](https://docs.nvidia.com/cuda/)。这些来源帮助理解设计取舍，不决定本项目必须复制的内部结构。具体实验需要引用源码时，在单元文档记录版本或提交。

**维护规则**：改变学习目标或单元顺序先改本 README；改变单元任务改 roadmap；改变共享边界改 architecture-design；只影响独立实验的细节留在该实验文档。旧章与新单元可以保留不同解法，直到它们需要通过共享核心交换数据。
