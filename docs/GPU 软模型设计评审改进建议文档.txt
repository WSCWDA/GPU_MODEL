# GPU 软模型设计评审改进建议文档

> 
> 基于全量 42 章分章设计 + 16 份顶层架构文档的评审结论，结合 **Mesa 图形驱动架构** 与 **MUSA 计算栈设计思想**，针对识别出的 7 大类核心问题，提供「保守修复 / 架构优化 / 重构升级」三档改进策略，供方案阶段决策选型。
> 文档定位：方案级决策参考，覆盖机制、架构、流程三类改进，兼顾短期可落地与长期可扩展性。

---

## 一、核心问题域与策略总览

表格

| 问题域 | 核心矛盾 | 策略 A 保守修复 | 策略 B 架构优化 | 策略 C 重构升级 |
| --- | --- | --- | --- | --- |
| 契约治理 | 冻结枚举与后续扩展冲突，缺少变更 / 退役流程 | 补登记表 + 扩展附录，最小改动 | 引入能力位 + 错误码分层 | 全量能力查询接口 + 分层错误体系 |
| MMIO 寄存器 | 三套地址表互斥，stateId 空间不足 | 统一偏移表，回修历史章节 | 分段规划 + 内存间接状态表 | 双 BAR 空间拆分，寄存器 / 内存彻底分离 |
| 计算分层 | 37 章与 38~42 章职责重叠，边界模糊 | 明确硬切分，删除重复内容 | 三层模型（HWI/UDI/API）正式化 | 计算与图形 PAL 统一，消除分支 |
| 编译器双后端 | 「逐字节一致」不可达，阻塞下游 | 降为语义一致 + 指标对齐 | 标准用例集对照，LLVM 退为参考 | 取消双后端，LLVM 作为生产路径 |
| 并行执行模型 | ticket 锁导致假并行，确定性与并行性矛盾 | CU 级并行、CU 内串行，修正判据 | 内存序正式化，结果一致不要求顺序一致 | 完整宽松内存模型 + 三级作用域同步原语 |
| 资源绑定 | stateId 瓶颈，粗粒度屏障能力不足 | 落实 EXTENDED 扩展，过渡槽标注待迁移 | Bindless 二期，按资源列表屏障 | 全 VA 化，取消描述符索引绑定 |
| 流程门禁 | 单点阻塞严重，串行推进效率低 | 解除 19 章对 20 章的强阻塞 | 两级门禁（阶段串行、模块并行） | 契约优先，全模块并行开发 |

## 二、分领域详细改进方案

### 1. 契约治理与扩展机制

#### 现状问题

- 第 1 章冻结 11 个 `Result` 枚举，后续章节新增 `Busy/OutOfStack/RegisterOverflow/InvalidIr` 共 4 个，与「冻结」定义冲突。
- 配置键无集中登记，各章私自新增，缺少分级与兼容性规则。
- 包号、opcode、stateId 仅靠 `bit-budget.md` 口头约束，无强制审计入口与变更记录。
- 缺少「契约退役」机制，旧 DoD 被替代后无标注，回归项边界不清。

#### 策略 A：保守修复（最小改动，不破坏现有规划）

**方案内容**

1. 在 `roadmap.md` 新增「契约扩展附录」，将 `Result` 从 11 个扩展到 16 个并重新冻结，明确后续新增必须走 ADR 增补，不得私自加枚举。
2. 建立三张集中登记表（统一放在 `bit-budget.md`）：包号与子操作码、stateId 与状态基址、全局配置键；所有新增必须先登记再实现，CI 增加编号审计门禁。
3. 引入 `SUPERSEDED` 标记：被替代的旧 DoD / 旧接口标注退役并指向新契约，回归时按新契约执行，旧契约仅保留兼容测试。
4. 配置键分为「核心冻结级」和「调试级」，只有核心级纳入契约冻结，调试级可按需新增。

**参考依据**：Mesa  DRM 接口的「版本号 + 扩展位」兼容机制，在主枚举不变的前提下通过子字段扩展。
**优点**：工作量最小，不改变现有开发节奏，所有已有章节只需补登记。
**缺点**：本质是延缓矛盾，空间耗尽后仍需再次扩容。

#### 策略 B：架构优化（能力位 + 分层错误码）

**方案内容**

1. 把 ADR-025 的「能力四档」正式化为**能力位掩码体系**：所有新增功能对应一个 capability bit，驱动通过 `QueryCapability` 查询，不再靠全局枚举冻结控制功能有无。新增功能默认关闭，通过能力位开启，不影响基线兼容性。
2. 错误码分层：
   - 顶层通用 `Result` 收缩为 8 个核心值（`Ok/InvalidArgument/NotSupported/OutOfMemory/NotMapped/Internal/Busy/Timeout`），永久冻结。
   - 模块级错误通过「错误详情结构体」返回（如编译错误、调度错误、页错误），不占用顶层枚举空间。
3. 包号扩展正式固化为「主类型 + 子操作码」两级：主类型 4bit 冻结，子操作码 16bit 按模块分配，每个模块有独立的子码编号空间，互不抢占。

**参考依据**：

- Mesa：Gallium3D 的 `pipe_cap` 能力查询体系，驱动按需暴露功能，前端不假设能力存在。
- MUSA：驱动 API 的错误码分层设计，通用返回码 + 模块级错误详情。
**优点**：彻底解决枚举空间不足的问题，兼容现有设计，扩展性显著提升。
**缺点**：需要统一修改所有模块的错误返回路径，中等工作量。

#### 策略 C：重构升级（全量能力查询体系）

**方案内容**

1. 建立完整的 `IDevice::QueryCapability` 接口，所有硬件功能、资源上限、支持的指令集、队列属性全部通过能力查询暴露，取消全局常量冻结的设计模式。
2. 错误体系升级为「错误码 + 错误上下文快照」，顶层只定义错误类别，具体信息由各模块自行扩展，通过统一日志与诊断接口输出。
3. 引入「特性等级」概念：初级 / 高级 A / 高级 B / 高级 C 对应不同的能力集，场景按特性等级运行，不再依赖单章门禁控制功能有无。

**参考依据**：Vulkan 物理设备特性查询、MUSA 设备属性查询体系。
**优点**：长期可扩展性最强，支持多代硬件 / 多配置兼容。
**缺点**：改动范围大，需要重构所有与「冻结常量」相关的设计，适合第二版架构迭代。

### 2. MMIO 与寄存器空间规划

#### 现状问题

- 第 2、3、10 章存在三套互斥 MMIO 偏移表：`0x04` 同时定义为 `RING_TAIL` / `DOORBELL`，`0x08` 同时为 `FENCE_VALUE_LO` / `FENCE_MON`，`0x30` 同时为 `RT_SIZE` / `DEV_RING_ID`。
- dword 索引与字节索引口径混用，B-042 整改不彻底。
- stateId 直接映射 MMIO 寄存器，8 个槽位严重不足，过渡槽 8~31 明确为临时方案。

#### 策略 A：保守修复（统一地址表，回修历史）

**方案内容**

1. 以第 10 章的分段设计为基准，输出**唯一权威 MMIO 地址表**，回修第 2、3 章的寄存器定义：
   - `0x00~0x0F`：Ring 控制区（基址、大小、头尾指针、doorbell）
   - `0x10~0x1F`：CP 控制与中断
   - `0x20~0x2F`：错误与性能统计
   - `0x30~0x3F`：设备全局信息（版本、环 ID、RT 尺寸移到 0x30 高 16bit）
   - `0x40~0x7F`：stateId 0~7 基址区（冻结）
   - `0x80~0xFF`：PSO 暂存区与固定功能状态
2. 统一 dword 索引口径，所有代码与文档强制对齐，CI 增加偏移断言校验。
3. 明确 `stateId 8~31` 为过渡预留，新增状态优先走内存间接表，不占用过渡槽。

**参考依据**：真实 GPU 寄存器的固定分段规划原则，控制 / 状态 / 统计分区。
**优点**：改动集中，一次性解决冲突，不改变架构模式。
**缺点**：未从根本解决 stateId 空间不足的问题，后期仍会遇到瓶颈。

#### 策略 B：架构优化（间接状态表 + 分段扩容）

**方案内容**

1. MMIO 空间扩容到 512 dword，分为三区：
   - 固定功能区（0x00~0x7F）：环、中断、错误、全局控制，永久冻结偏移。
   - 状态基址区（0x80~0xFF）：只存 8 个根指针，指向 GPU 内存中的状态表、描述符表、管线配置表等。
   - 扩展功能区（0x100~0x1FF）：Copy 引擎、显示引擎、计算引擎的专用控制寄存器。
2. 所有 stateId 全部改为「内存间接索引」：MMIO 只存状态表基址，具体状态通过 `SET_STATE_TABLE_INDEX` 访问 GPU 内存中的状态数组，彻底取消 stateId 数量限制。
3. 建立寄存器命名规范：`SECTION_XX_REG_YY`，统一宏定义，避免重复定义。

**参考依据**：AMD GCN 架构的 MMIO 设计，大量状态通过内存表管理，MMIO 仅做控制与基址指针。
**优点**：彻底解决 stateId 瓶颈，寄存器规划清晰可扩展，符合现代 GPU 设计思想。
**缺点**：需要修改所有状态读写路径，工作量中等。

#### 策略 C：重构升级（双 BAR 空间设计）

**方案内容**

1. 模拟真实 PCIe BAR 空间，拆分为两个独立地址空间：
   - **BAR0：寄存器空间**（小容量，256 dword），仅用于控制、中断、门铃、错误、基址指针，所有寄存器偏移永久冻结。
   - **BAR1：内存映射空间**（大容量，GPU 可访问），存放命令环、描述符堆、状态表、固件数据，硬件通过 DMA 访问，不占用 MMIO 寄存器偏移。
2. 硬件单元内部状态全部通过 BAR1 内存管理，MMIO 只负责启动、停止、复位、查询状态四类操作。
3. 引入「寄存器版本号」机制，后续新增寄存器通过版本号兼容，不破坏旧偏移。

**参考依据**：PCIe 标准 BAR 空间划分、NVIDIA/AMD 真实 GPU 的寄存器 / 显存分离设计。
**优点**：架构最合理，彻底解决空间不足与冲突问题，长期可扩展性最强。
**缺点**：改动涉及地址空间模型，影响面广，适合架构大版本升级。

### 3. 计算管线与驱动分层边界

#### 现状问题

- 第 37 章与 38~42 章存在大量重复定义：`DISPATCH` 包格式、参数布局、间接派发、LDS/barrier 语义两边各写一遍，8 对 DoD 判据几乎逐字相同。
- 边界约定「37 章只做硬件通路，不做驱动对象」未落到任务与 DoD 中，37 章出现了驱动层参数打包逻辑。
- HLI 接口是否新增两边口径不一，存在反向修改 HLI 的风险。

#### 策略 A：保守修复（硬切边界，删除重复）

**方案内容**

1. 明确一刀切边界：
   - **第 37 章（硬件计算管线）**：只定义硬件级内容 ——`DISPATCH` 命令包二进制格式、workgroup 调度逻辑、wave 映射、LDS 硬件分配、barrier 硬件语义、间接派发命令格式、查询统计寄存器。验收方式：直连 HLI 构造命令包，验证硬件通路正确性。**严禁出现任何驱动对象（Context/Module/Function/Stream）**。
   - **第 38~42 章（计算驱动）**：只做驱动层内容 —— 对象生命周期管理、模块二进制解析、kernel 参数打包、stream 队列映射、event 同步封装。验收方式：通过驱动 API 提交，结果与 37 章直连 HLI 逐值等价。
2. 删除 37 章中所有驱动层描述与重复判据，把参数打包、模块加载等内容全部后移到 39~40 章。
3. 明确 HLI 接口在 35.1 收口后冻结，38~42 章**只能复用已有 HLI 接口，不得新增**，所有驱动层能力通过组合已有接口实现。

**参考依据**：MUSA 分层设计：Kernel 硬件层 -> Driver 驱动层 -> Runtime 运行时层，每层边界清晰，下层不感知上层对象。
**优点**：改动最小，边界清晰，符合顶层 ADR-047/048 的原定案。
**缺点**：只是切割内容，没有提升架构统一性。

#### 策略 B：架构优化（三层模型正式化）

**方案内容**

1. 正式建立三层计算栈，每层有独立的接口契约：

表格

| 层级 | 对应章节 | 职责 | 接口 |
| --- | --- | --- | --- |
| HWI 硬件接口层 | 37 | 命令包构造、硬件调度、同步原语 | 纯命令级 API，无对象 |
| UDI 用户驱动层 | 38~42 | 对象管理、二进制加载、参数打包、异步提交 | MUSA 风格对象 API |
| API 运行时层 | 远期扩展 | 高级 Runtime 功能、流并行、内存池 | 应用层 API |
2. HWI 层接口一次冻结，UDI 层完全基于 HWI 封装，不新增硬件能力。两层各有独立的单元测试与验收用例，S18/S19 分别在 HWI 层和 UDI 层各有一套，最终做双入口等价校验。
3. 统一错误码、内存分配、同步原语在 HWI 层的实现，UDI 层只做封装转换。

**参考依据**：MUSA 完整软件栈分层：`musaRuntime -> musaDriver -> 内核态驱动 -> 硬件`，每层职责单一，可独立替换。
**优点**：架构清晰，可测试性强，便于后续扩展不同的上层 API。
**缺点**：需要补充层间接口契约，中等工作量。

#### 策略 C：重构升级（PAL 统一，图形计算一体化）

**方案内容**

1. 参考 Mesa Gallium3D 的统一管线设计，把计算驱动完全融入现有 PAL 层，不再作为独立分支：
   - 资源、视图、堆、内存分配：图形与计算共用一套实现。
   - 管线对象：计算管线是图形管线的同构扩展，共用绑定、状态、屏障机制。
   - 队列与同步：图形队列与计算队列共用同一套命令流、fence、semaphore 机制。
2. 第 37 章变为「计算管线硬件通路」，第 38~42 章变为「计算管线 PAL 封装」，彻底消除重复的资源管理、内存管理、同步原语实现。
3. 最终实现：新增计算功能不需要新增独立驱动框架，只需要在现有 PAL 上扩展管线类型与命令包。

**参考依据**：Mesa Gallium3D 设计，图形与计算共用 pipe_context，统一资源、状态、命令模型。
**优点**：代码复用率最高，架构最统一，长期维护成本最低。
**缺点**：改动范围大，需要对齐图形与计算的所有对象模型，适合架构重构阶段。

### 4. 编译器双后端一致性验收

#### 现状问题

- 第 19 章要求「手写后端与 LLVM 后端逐字节一致」，技术上不可达：独立 emitter 必须复刻对方的指令选择、寄存器分配、块序、立即数展开才能逐字节相同，一旦完全相同就失去了对照意义。
- 该要求作为 ADR-012 门禁，直接阻塞第 20 章及后续所有高级图形功能，形成单点瓶颈。

#### 策略 A：保守修复（降标验收，解除阻塞）

**方案内容**

1. 将验收标准从「逐字节一致」调整为**「语义一致 + 关键指标对齐」**：
   - 硬判据：相同 IR 输入，执行结果与参考模型逐字节一致（零容差）。
   - 软对齐：指令数差异 ≤ 5%，VGPR 使用数差异 ≤ 2，溢出数一致，控制流结构等价。
2. 保留 LLVM 后端的对照定位，但从「阻断门禁」降级为「回归告警」：出现差异时输出报告，不阻塞下游章节开发，只作为质量优化项。
3. 明确第 19 章不阻塞第 20 章开工，手写后端作为生产路径，LLVM 后端并行开发。

**参考依据**：Mesa 编译器回归的思路：正确性是硬标准，代码生成质量是软指标，不要求不同后端二进制一致。
**优点**：改动最小，立刻解除单点阻塞，保留对照机制。
**缺点**：双后端对照的严谨性下降。

#### 策略 B：架构优化（标准用例集 + 语义等价校验）

**方案内容**

1. 建立专门的编译器验收用例集 `S0_compiler`，覆盖 4 大类：算术与内建、控制流、内存访问、发散与同步，每类 10~15 个标准用例。
2. 验收规则升级为：
   - 所有标准用例，两后端执行结果必须零容差一致。
   - ABI 分区合规性检查：不得侵占固定分区，uniform 区、输入输出区位置正确。
   - 编码格式合规：所有指令符合 64bit 编码规范，无非法字段。
   - 不要求指令序列、寄存器分配逐字节相同。
3. LLVM 后端定位为「参考验证后端」，用于交叉校验手写后端的语义正确性，不作为生产路径。

**参考依据**：Mesa Piglit 测试集 + LLVM lit 测试的设计思想，用标准用例集保证编译器正确性，而非二进制比对。
**优点**：验收科学合理，既保证正确性，又符合编译器行业惯例。
**缺点**：需要新增一套标准用例集，中等工作量。

#### 策略 C：重构升级（LLVM 为主，手写保留最小集）

**方案内容**

1. 取消「双后端并行生产」的模式，将 LLVM 后端升级为**生产级后端**，负责全量功能的代码生成。
2. 手写后端只保留最小指令子集（约 20 条），用于教学、调试和最小系统引导，不再作为全功能生产路径。
3. 第 18 章收缩为「手写最小后端」，第 19 章升级为「LLVM 生产后端」，验收标准改为：通过全部编译器测试集，性能与代码质量达标。

**参考依据**：Mesa 从自研 TGSI 转向 NIR + LLVM 的演进路线，工业界最终都会收敛到成熟编译器基础设施。
**优点**：技术路线最合理，长期维护成本低，便于后续扩展优化、新指令、新特性。
**缺点**：推翻原有双后端规划，对前期工作有一定废弃，需要调整研发排期。

### 5. 并行执行模型

#### 现状问题

- ticket 自旋锁设计导致 CU 内实际串行执行，`maxWavesPerCu=16` 无意义，组内 barrier 的「同时到达」语义永远不会触发，无法暴露并行 bug。
- `fetch_add` 领取 wave 的顺序依赖线程调度，与「serial/parallel 硬判据零容差」的要求矛盾。
- 内存作用域与可见性规则不明确，并行正确性缺少正式定义。

#### 策略 A：保守修复（CU 级并行，修正判据）

**方案内容**

1. 调整并行粒度：**SE 间多线程并行，CU 内单线程串行**。每个 CU 分配一个 worker 线程，CU 内部 wave 按固定顺序调度，不做并发抢占。
2. 去掉 ticket 锁设计，改为每个 CU 独立的就绪队列，按固定轮转顺序调度 wave，保证调度顺序确定性。
3. 修改 D31.12 等判据：不再要求 wave 领取顺序逐项一致，只要求**最终内存输出结果零容差一致**；中间调度顺序、命中率、耗时属于软观测，不纳入硬判据。
4. 组内 barrier 的验证通过「多 CU 跨组」场景实现，同一 CU 内串行天然满足 barrier 语义。

**参考依据**：早期 GPU 模拟器的常用设计，以 CU 为并行单位，内部保持串行以简化正确性验证。
**优点**：改动小，既保留并行验证能力，又维持确定性，不破坏双策略一致的规则。
**缺点**：CU 内的并行竞争无法验证，波间并发 bug 难以暴露。

#### 策略 B：架构优化（正式内存序，结果一致即可）

**方案内容**

1. 引入正式的**内存一致性模型**，明确三级可见性规则：
   - wave 内：指令级顺序一致，所有 lane 同步执行。
   - workgroup 内：barrier 之前的所有写操作，barrier 之后所有 lane 可见。
   - device 级：fence / 屏障之后的写，后续命令可见。
2. 双策略一致性规则升级：
   - 硬判据：只要最终内存结果符合内存模型规则，即为正确，不要求中间执行顺序、原子操作的中间步骤一致。
   - 原子操作的最终结果必须唯一（如原子加的总和确定），但中间累加顺序不做要求。
3. 放开 CU 内 wave 并行：支持多 wave 并发执行，通过原子操作与 barrier 保证正确性，用内存模型规则校验正确性，而非和串行版本逐字节比对。

**参考依据**：Vulkan Memory Model、MUSA 内存一致性模型，现代并行编程的标准设计。
**优点**：符合真实 GPU 的并行行为，能真正验证并行正确性，设计更专业。
**缺点**：需要重写所有并行相关的判据，验证复杂度上升。

#### 策略 C：重构升级（宽松内存模型 + 三级同步原语）

**方案内容**

1. 建立完整的 GPU 内存模型：
   - 三种作用域：wave /workgroup/device
   - 三种内存语义：acquire /release/acquire-release
   - 两类同步原语：barrier（组内执行同步）、fence（内存可见性同步）
2. 策略 A（串行）作为「参考模型」，提供最强一致性的正确结果；策略 B（并行）只需要满足内存模型规范，不需要和串行结果逐字节一致。
3. 新增一套内存模型验证用例，覆盖写后读、原子累加、屏障可见性等场景，验证并行执行的正确性。

**参考依据**：C++ Memory Model、CUDA Memory Model、MUSA 同步原语体系。
**优点**：最接近真实工业级设计，技术深度最高，可验证复杂并行算法。
**缺点**：改动最大，需要重构整个执行模型与校验体系，适合架构第二版。

### 6. 资源绑定与状态管理

#### 现状问题

- stateId 直接映射 MMIO，8 个固定槽位严重不足，过渡槽明确为临时方案。
- 描述符堆一期能力有限，采样器、纹理、缓冲区分别绑定，路径不统一。
- 资源屏障为粗粒度全局掩码，无法做精细的资源级同步。

#### 策略 A：保守修复（落实 EXTENDED 扩展，严控过渡槽）

**方案内容**

1. 所有新增绑定类命令全部走 `EXTENDED(0x0F)` 子操作码，不再抢占顶层包号。
2. stateId 0~7 永久冻结，8~31 过渡槽明确标注「仅用于迁移过渡，禁止长期依赖」，新增状态优先走「内存间接状态表」，MMIO 只存根指针。
3. 采样器统一并入 stateId 5 描述符堆，复用绑定路径，不新增独立绑定命令。
4. 在 `bit-budget.md` 中新增描述符、状态的编号审计项，所有新增必须先登记。

**优点**：改动小，落实已有规划，延缓空间瓶颈。
**缺点**：未从根本解决绑定点不足的问题。

#### 策略 B：架构优化（Bindless 二期，按资源屏障）

**方案内容**

1. 升级到 Bindless 二期：所有资源（纹理、采样器、UAV、CBV）全部放入统一描述符堆，硬件只需要一个基址寄存器，shader 直接通过索引访问，彻底消除绑定点数量限制。
2. 资源屏障从「全局粗粒度掩码」升级为「资源列表级屏障」：屏障命令携带资源数组，只 flush/invalidate 涉及的资源范围，性能更优，正确性更精准。
3. 根签名只负责描述符堆的槽位映射，不再管理单个资源绑定。

**参考依据**：Mesa 对 Vulkan Descriptor Set 的实现、现代 GPU 的 Bindless 设计。
**优点**：彻底解决绑定点瓶颈，符合现代图形 API 设计方向。
**缺点**：需要修改绑定、描述符、屏障全链路，中等工作量。

#### 策略 C：重构升级（全 VA 化，取消描述符索引）

**方案内容**

1. 参考 MUSA 统一内存模型，所有资源访问直接通过虚拟地址（VA）进行，取消描述符堆、描述符索引、绑定点的概念。
2. Shader 中直接使用指针访问资源，硬件通过 MMU 翻译地址，自动处理越界、权限校验。
3. 资源状态与屏障全部按 VA 范围管理，不需要描述符中转。

**参考依据**：CUDA/MUSA 的指针式资源访问，计算统一地址空间设计。
**优点**：编程模型最简单，硬件逻辑最统一，彻底消除绑定相关的所有复杂度。
**缺点**：改动颠覆现有图形管线的绑定模型，适合计算优先的架构，图形管线适配成本高。

### 7. 阶段门禁与研发流程

#### 现状问题

- 严格串行推进导致单点阻塞（如 19 章卡 20 章），整体研发效率低。
- 缺少横向模块联调节点，容易到端到端阶段才发现接口不匹配。
- 简化项的替换、审计、退役没有标准化流程。

#### 策略 A：保守修复（解除单点阻塞）

**方案内容**

1. 保留「大阶段串行」原则（初级 → 高级 A → 高级 B → 高级 C…），但阶段内的章级门禁放开强依赖。
2. 典型调整：第 19 章不阻塞第 20 章开工，20 章可以基于手写后端开发，19 章完成后补回归验证；只要上游契约（接口、包格式、ABI）冻结，下游即可开工。
3. 新增「契约冻结里程碑」，作为下游开工的前置条件，替代「整章验收通过」。

**优点**：改动最小，在不破坏整体流程的前提下缓解阻塞。
**缺点**：并行度提升有限。

#### 策略 B：架构优化（两级门禁，模块并行）

**方案内容**

1. 建立「阶段门禁 + 模块门禁」两级体系：
   - **阶段门禁**（初级 / 高级 A/B/C/D/E/F）：严格串行，必须三条件（场景全绿、契约冻结、回归不退化）全满足才能进入下一阶段。
   - **模块门禁**（单章）：阶段内可以并行开发，只要对应子系统的契约冻结即可开工，最终阶段门禁统一验收。
2. 例如高级 B 阶段中，「编译器线（17~19）」与「执行模型线（15~16）」可并行，「图形管线线（20~28）」与「计算线（37~42）」可并行。
3. 每个阶段中期设置一次「契约联调节点」，集中校验所有模块的接口一致性。

**参考依据**：Mesa 多模块并行开发的分支管理模式，子系统独立迭代，主干定期合并。
**优点**：并行度显著提升，符合多团队协作模式。
**缺点**：需要更强的契约管理与联调机制。

#### 策略 C：重构升级（契约优先，全并行开发）

**方案内容**

1. 采用「契约优先」开发模式：项目第一阶段先完成所有层间接口契约的定义与冻结（`IMemorySubsystem`、`IEngine`、`IShaderArray`、HLI、KMD/FW 接口等）。
2. 所有模块可以完全并行开发，各自基于契约做单元测试与契约测试，不需要等待上游模块实现。
3. 最后进行端到端集成与回归验收，阶段划分从「功能串行」变为「集成里程碑」。

**参考依据**：大型软件系统的接口优先开发模式，业界通用的并行研发方法。
**优点**：研发效率最高，适合多团队大规模并行。
**缺点**：对契约设计质量要求极高，前期需要投入大量接口设计工作。

### 8. 错误处理与复位体系

#### 现状问题

- 看门狗基于墙钟，在单线程模拟中无法触发，失去验证意义。
- 复位路径不闭环：页错误、非法包只记录错误，没有完整的复位 - 恢复 - 重跑流程。
- 错误记录字段不统一，各章错误定位信息口径不一。

#### 策略 A：保守修复（指令预算看门狗，统一错误字段）

**方案内容**

1. 看门狗改为「指令预算机制」：每个提交配置最大允许指令数，单波执行指令数超过阈值即触发超时中断，模拟看门狗行为，可稳定复现超时场景。
2. 补充「引擎级软复位」流程：错误发生后可复位对应引擎，清空内部状态，重新接收命令，不影响全局设备。
3. 统一错误记录结构体：所有模块错误都包含 `unit, packetType, dwordOffset, va, errorCode` 五个字段，统一日志格式。

**优点**：改动小，立刻解决看门狗无法触发的问题。
**缺点**：只是功能补全，没有体系化设计。

#### 策略 B：架构优化（三级错误体系）

**方案内容**

1. 建立三级错误处理机制：
   - **可恢复错误**（参数非法、越界、未映射）：中止当前提交，返回错误码，状态不变，后续提交可正常执行。
   - **引擎级错误**（挂死、超时、数据损坏）：触发引擎级复位，清空该引擎所有上下文，其他引擎不受影响。
   - **全局致命错误**（总线错误、固件崩溃）：触发全局复位，整个设备重启。
2. 第 36 章按三级错误体系重构，覆盖错误注入、检测、复位、恢复、验证全流程。
3. 错误码与错误记录统一规范，支持诊断工具解析。

**参考依据**：Mesa DRM GPU Reset 机制、Linux 驱动的错误分级处理。
**优点**：体系完整，符合真实驱动的设计，可验证性强。
**缺点**：需要重构所有错误处理路径，工作量中等。

#### 策略 C：重构升级（完整故障注入与恢复体系）

**方案内容**

1. 建立完整的故障注入测试框架，支持在任意位置注入错误（非法包、页错误、超时、数据损坏），验证复位恢复流程。
2. 支持按上下文复位：出错只杀死对应上下文，不影响其他上下文，符合真实 GPU 的隔离性。
3. 错误记录带完整上下文快照（寄存器、命令指针、状态），支持事后调试与溯源。

**参考依据**：企业级 GPU 驱动的 RAS 设计、MUSA 错误隔离与恢复机制。
**优点**：专业度最高，覆盖最完整，接近工业级质量。
**缺点**：开发工作量大，适合后期质量提升阶段。

结合项目处于方案阶段的特点，建议采用「**R0 定基础 + R1 优架构 + R2 提质量**」三步落地策略，优先解决阻塞性问题，再逐步升级架构。
